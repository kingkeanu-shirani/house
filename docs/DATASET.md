# Trajectory and preference-pair dataset

`house_sim/eval/dataset.py` (contract: docs/EVAL_CONTRACTS.md section D) turns verified task specs into training data
for household agents: supervised trajectories, trajectory-level and step-level preference pairs, and critiques of
failing trajectories. Everything is produced offline by the simulator in realistic perception, so observations and
commands use opaque handles and perceived (bucketed / noisy / inspected) values exactly as an evaluated agent sees
them. Standard library only; no network access anywhere.

## Provenance and license

* **Synthetic.** Every record is generated by this project's household simulator (`house_sim`) running the project's
  own task specs (`tasks/authored/*.json`) in procedurally generated houses. Seeds, house layouts, residents, objects
  and outcomes are simulated.
* **Task text** (instructions and phrasings) derives from the project's household catalog
  (`catalog/raw/household_catalog.txt`), i.e. from the user's inputs, via the spec authors' phrasings.
* **No real household data**: no real homes, people, images, audio, sensor logs or personal information.
  Resident names and ids are simulated placeholders.
* **License**: the dataset carries the license of this project. The project does not ship a LICENSE file yet; choose
  one before redistributing exports outside the project. `manifest.json` repeats this statement (`provenance`,
  `license`) and records the fingerprints of the code that produced the data (simulator, evaluation tooling and
  perception tiers; see "Fingerprints").

## Commands

```
python -m house_sim --export-dataset OUT_DIR [options]       # or: python tools/export_dataset.py OUT_DIR [options]
python -m house_sim --validate-dataset PATH [--no-deep | --allow-static]   # or: python tools/validate_dataset.py PATH
```

| option | default | meaning |
|---|---|---|
| `--formats` | all four | comma list of `sft, pairs_trajectory, pairs_step, critique` |
| `--split` | `train` | `train` or `dev`; **`test` is refused** |
| `--seeds-per-entry N` | 2 | train seeds per entry (`splits.train_seeds(catalog_id, N)`) or the first N dev seeds |
| `--seeds S1,S2` | | explicit seeds (each refused if private / test, and checked against the split's range) |
| `--max-pairs N` | none | cap for each pair format, taken round-robin over catalog entries |
| `--kinds`, `--domains` | all | comma lists (catalog kind: task, appendix, adaptability, primitive, variation; domain = authored file prefix, e.g. `cleaning`) |
| `--sections` | all | section name or substring; `;` separates several; repeatable |
| `--catalog-ids` | all | comma list of catalog ids |
| `--obs compact\|full` | `compact` | observation rendering (below) |
| `--workers N` | cpu-1 | parallel seed jobs (output is identical for any N) |
| `--verify-now` | off | verify the selected specs on the dev seeds now instead of trusting evidence |
| `--overwrite` | off | export: replace a previous export in OUT_DIR (below); without it a non-empty OUT_DIR is refused |
| `--no-deep` | off | validate: static checks only (no environment is rebuilt) |
| `--allow-static` | off | validate: accept records whose environment cannot be rebuilt with static checks only (warning instead of error) |
| `--json OUT` | | also write the manifest (export) or the validation report (validate) as JSON |

Python API: `export(out_dir, formats=..., split="train", seeds_per_entry=2, max_pairs=None, kinds=None, domains=None,
sections=None, obs="compact", workers=None, catalog_ids=None, seeds=None, verify_now=False, overwrite=False) ->
manifest` and `validate(path_or_dir, deep=True, allow_static=False) -> report` (`report["ok"]`, `error_counts`,
`errors`, `warnings`, the current and the dataset's fingerprints, `stale` / `harness_stale` / `perception_stale`,
`deep_checked_records`). Exit status: export 0 when records were written (1 when nothing qualified, 2 on refused
arguments, a refused output directory or an unusable `house_sim/eval/splits.py`); validate 0 valid / 1 invalid.

### Output directory

`OUT_DIR` must be missing or empty. Re-exporting into a previous export needs `--overwrite` (`overwrite=True`): the
exporter then deletes `manifest.json` first and every `<format>.jsonl` (also the formats it does not write this time)
before writing, and writes `manifest.json` last, so the directory never mixes files of two exports and an interrupted
export has no manifest (and does not validate). A directory holding anything else (other files or subdirectories;
operating-system metadata such as `desktop.ini` is ignored) is refused even with `--overwrite`. Both checks run before
anything is verified or exported, and again right before writing.

## Which specs and seeds

1. **Verified specs only.** By default a spec qualifies when `reports/verification.jsonl` has a passing record whose
   `implementation_hash` equals `house_sim.audit.fingerprint()` and whose `spec_hash` equals the current
   `house_sim.tasks.verify.spec_hash(spec)` (the same rule as the coverage report). When `splits.verified_specs()`
   exists it is used as an additional cross-check. Because other work on the simulator makes evidence stale quickly,
   `--verify-now` runs `house_sim.tasks.verify.verify_many` on the dev seeds (0, 1, 2, 41, 97) in each spec's own
   perception mode and uses only specs that pass. Unverified specs are never exported; the manifest lists them with
   the reason (`verification.unverified`). Specs are read without writing any file; a catalog id authored in two
   files is ambiguous and excluded ("excluded: authored twice (...)") while the rest of the catalog still exports.
2. **Seeds.** Train seeds by default (`splits.train_seeds(catalog_id, N)` in `[TRAIN_BASE, PRIVATE_BASE)`), dev seeds
   optionally (`splits.dev_seeds`). Test data is never exported: the test split, seeds `>= PRIVATE_BASE` (no key
   needed) and seeds in the private test manifest (`splits.guard_not_test`) raise `ValueError("test seed refused")`
   before anything runs; when the private manifest exists but cannot be read every seed is refused (fail closed).
   Explicit `--seeds` must be distinct and inside the split. **`house_sim/eval/splits.py` is required**: when it
   cannot be imported (for example half-saved by another edit) or lacks the contract functions, export raises
   `SplitsUnavailable` (CLI exit 2) and validation fails with a `splits` error. There is no stand-in, because a
   different seed formula would produce different data under the same code fingerprint. The manifest records
   `splits_source` (`house_sim.eval.splits`).
3. **Per-seed re-verification in realistic mode.** For each (spec, seed) the exporter checks, in fresh
   `make_env(config, task, seed, perception="realistic")` environments: the initial state fails, waiting out the budget
   fails, the reference plan succeeds strictly (no refused step) and every report value it makes was perceived
   (`verify.perceivability_gaps`). Otherwise the seed is skipped. A wrong plan is used only if it ran, issued at least
   one command and fails on that seed.

## How episodes are recorded

Plans run through `runner.build` + `make_env(perception="realistic")` + `run_plan`; the runner translates the plans'
true ids into handles, as an agent would use them. The exporter wraps `env.step`, so every primitive step (skills
expand to primitives) is captured with:

* the **observation the agent had before the step** (the reset observation, then each step's returned observation),
* the **command exactly as issued** (`{"action": ..., "target": "obj_…", "destination": ..., params}`; empty target /
  destination omitted),
* the **result the agent saw**: `{"ok", "message", "category"}` with the agent-facing message (handles, never true ids).

The record's `instruction` is the instruction **as the agent receives it** (the observation's `instruction`, with ids
translated and things not yet perceived shown as "something"), not the raw `task["instruction"]`, which can name true
ids.

Every observation, command, message and the instruction is audited live with `tools/perception_audit.py`
(`check_obs`, `check_message`; local equivalents if that tool cannot be loaded), plus a scan for underscore /
`secret_fields` keys and for true ids: every entity id seen so far in the episode (an entity removed by a step can
still be named in that step's message), tokens that start with `<registered type>_<n>` and tokens shaped like an id
the house generator emits (the static id vocabulary, see "Validator"), so the live audit is at least as strict as
the validator. Episodes with an `id`, `secret` or `hidden` leak are dropped (`audit.episodes_dropped`);
`tier`, `hazard` and `message` findings are counted as warnings (`audit.warnings`). Evaluator failure labels are
translated to handles before they are stored (e.g. `broke:obj_8cacd041`).

## Formats

One JSONL file per format (UTF-8, one JSON object per line, keys sorted). Every record has `format`, `id` and `meta`.

**sft** (`sft.jsonl`, reference plans):
```json
{"format": "sft", "system": "You control a household robot ...", "instruction": "Connect the streaming box ...",
 "turns": [{"observation": {...}, "action": {"action": "approach", "target": "obj_ef148b47", "avoid": [...]},
            "result": {"ok": true, "message": "Approached obj_ef148b47", "category": ""}},
           ...,
           {"observation": {...final...}, "action": {"action": "done"}}],
 "outcome": {"success": true, "goal_fraction": 1.0, "steps": 5, "time_s": 61.0, "score": 1.0}, "meta": {...}}
```
The last turn is always `{"action": "done"}` on the final observation (the harness's end-of-episode command).

**Multi-phase tasks** (kernel v3.1, docs/TASK_SPEC.md "Phases") are one episode in the harness's protocol: the
agent ends each phase with `{"action": "done"}`, recorded as a turn (or a pairs / critique step) whose result also
carries `"phase": {"ended": <id>, "active": <next id or null>, "waiting": <bool>}`; the observation after it shows
the next phase's instruction and request. The done that ends the last phase is the episode's last turn (it keeps
its result; no further done follows). Their records add `meta.phases` (the phase ids) and the sft outcome
`"phases": [{"id", "success", "steps", "time_s", "end_reason"}]`; `unmet_success` names phase criteria as
`"<phase id>:<index>"`. This is an addition within `house-dataset-v3` (single-phase records are unchanged).

**pairs_trajectory**: `{"prompt": {"instruction", "observation": <initial>}, "chosen": [reference commands],
"rejected": [wrong-plan commands], "rejected_reason": {"wrong_plan": <spec's wrong-plan name>, "failures":
[evaluator labels], "goal_fraction", "unmet_success": [indices of unmet success predicates], "refused_steps"}}`.

**pairs_step**: at the first divergence of the two command sequences, `{"context": {"instruction", "observation":
<observation at the divergence>, "history": [{"action", "result"} so far]}, "chosen": <next reference command>,
"rejected": <next wrong command>, "reason": {...rejected_reason..., "divergence_step": k, "divergence":
"different_action" | "premature_done" | "extra_action"}}`. `premature_done`: the wrong plan stopped where the
reference continues (rejected = done); `extra_action`: the reference was finished (chosen = done). Pairs whose
observations at the divergence differ (compared on the full observation) are skipped; with identical command
prefixes in a deterministic simulator they never should.

**critique** (wrong plans): `{"trajectory": {"instruction", "initial_observation", "steps": [{"action", "result"}],
"final_observation"}, "verdict": "fail", "reasons": {...same as rejected_reason...}}`.

**meta** (all formats): `catalog_id, section, kind, domain, family, title, risk_level, fidelity, spec_hash,
code_fingerprint, harness_fingerprint, perception_fingerprint, split, seed_tag, seed (train/dev only), variant,
perception ("realistic"), camera ("room" | "geometric"), obs, schema ("house-dataset-v3"), source ("reference" |
"wrong")` and, for wrong-plan records, `wrong_plan, wrong_index`. `camera` is the camera mode the episode ran in (the
spec's own, else the kernel default, "room" until the geometric camera becomes the realistic default).

### Format versions

The validator accepts only the current `schema`; a dataset of an older version does not validate and is re-exported
(the export is deterministic, so nothing is lost but time).

| schema | what changed |
|---|---|
| `house-dataset-v1` | the first exporter's format |
| `house-dataset-v2` | `harness_fingerprint` and `perception_fingerprint` in every manifest and record |
| `house-dataset-v3` | kernel v3.0 (tier-1 physics, camera and robot body): the observations an agent sees changed: realistic `obs.robot` is the robot's proprioception (an integer `battery` gauge equal to the top-level `obs.battery`, `battery_state`, `runtime_min_est`, `range_m_est`, `battery_temp`, `camera`, `hearing`, `network`, `arms`, `legs`, `load`, `grip`, `hand_soil`, detected `faults`; `pos` null while the robot is lost), physics sounds are `{kind, source_hint, loudness[, count]}` with words only, sensor gates empty what a powered-down, blind or deaf robot cannot perceive, and geometric-camera episodes add `obs.camera`, `obs.lidar` and per-record `view` blocks (docs/PERCEPTION.md); `meta.camera` is required (v2 records could omit it) |

### Observations

* `full`: the realistic observation verbatim.
* `compact` (default): null, false and empty (`[]`, `{}`) values inside dicts are omitted (absent means null / false /
  empty), as are top-level keys that duplicate others (`instruction` when equal to the record's instruction,
  `battery` / `stopped` when equal to the robot's, `weather_now` when equal to `weather`). List elements and all other
  values are kept, so nothing an agent could perceive is lost. About 15-20 KB per observation in a typical room.
  Battery rule (v3): in realistic perception the top-level `battery` and `obs.robot.battery` are the same integer
  gauge (also while the robot is powered down), so a compact observation never repeats the top-level `battery`; read
  `robot.battery`. Only an environment built without the `proprioception` sensor (its `obs.robot` keeps `pos`,
  `posture` and `hands`) keeps the top-level value.

## Dedup, ordering, determinism

* `id` = sha256 of the record without `id` and `meta` (first 32 hex digits); duplicates within a format are dropped
  (first occurrence kept) and counted (`formats.<fmt>.duplicates_removed`).
* Order: catalog order, then seed order, then wrong-plan order. `--max-pairs` keeps a deterministic round-robin across
  entries (`formats.<fmt>.capped`).
* The same options and code (all three fingerprints equal, see "Fingerprints") produce byte-identical files and
  manifest (no timestamps; independent of `--workers` and `PYTHONHASHSEED`). The manifest omits the output path and
  worker count for that reason.

## manifest.json

`schema, generator, code_fingerprint, harness_fingerprint, perception_fingerprint, actions_fingerprint,
splits_source, options, verification {mode, seeds | evidence_file, candidates, verified, unverified}, formats
{<fmt>: {file, records, bytes, sha256, duplicates_removed, capped}}, size {total_records, total_bytes,
mean_record_bytes, max_record_bytes}, counts {entries_selected, entries_verified, entries_exported, seed_jobs,
seeds_exported, records, skip_reasons}, entries {<catalog_id>: {seed_tags, records}}, skipped [{catalog_id, seed_tag,
wrong_plan?, reason}] (entity ids masked), audit, provenance, license`.

### Fingerprints

Every manifest and every record's `meta` carry three fingerprints; the validator compares them with the current code:

| key | what it digests | when it differs from the current code |
|---|---|---|
| `code_fingerprint` | `house_sim.audit.fingerprint()`: simulation code and data (not `house_sim/eval`) | `stale` warning |
| `harness_fingerprint` | `house_sim.audit.harness_fingerprint()`: the evaluation tooling `house_sim/eval/**`, i.e. this exporter and `splits.py` | `stale_harness` warning |
| `perception_fingerprint` | `dataset.perception_fingerprint()`: what decides secret / never-tier fields (`kernel/realism.py` default tiers, hidden name patterns and tier functions; per type its ancestor chain, `perception` block, `secret_fields`, `_perception`; domain `field_tiers`) | `stale_perception` warning; non-core never-tier findings become warnings (below) |

So two exports with the same options and the same three fingerprints are byte-identical, and an edit to the
exporter or to `splits.py` shows up in `harness_fingerprint` even though `code_fingerprint` excludes `house_sim/eval`.
Within one dataset every record must carry the manifest's three values (`mixed_fingerprint` error otherwise).

## Validator

`validate()` / `--validate-dataset` checks a directory (with `manifest.json`) or a single JSONL file:

* **directory contents**: a dataset directory holds `manifest.json` and the files it lists (`formats.<fmt>.file`
  must be `<fmt>.jsonl`), nothing else. Any other `.jsonl` / `.ndjson` file, anywhere below the directory (a stale
  format file from an earlier export, a format removed from `manifest.formats`, an extra file), is an
  `unlisted_file` **error** and is validated anyway, so its own problems (test-split records, leaks, ...) are
  reported too. Other data-like files (`.json`, `.csv`, `.parquet`, archives, ...) are `unlisted_file` errors as well;
  anything else (a README) is an `unexpected_file` warning; operating-system metadata files are ignored;
* **schema** of every format (commands, results, done only last unless it is a phase end carrying `phase`,
  divergence step = history length, ...) and
  `meta.schema`;
* **content hash** (`id` recomputed) and **duplicates**;
* **splits**: the manifest's `splits_source` must be `house_sim.eval.splits`; no `test` split or `test:` tag, no
  seed `>= PRIVATE_BASE` or in the private test manifest; the seed matches its split, its tag
  (`splits.seed_tag`) and the manifest's options: with `options.seeds` it must be one of them, otherwise one of
  the entry's first `seeds_per_entry` seeds of `splits.train_seeds` / `dev_seeds` (`off_schedule_seed` error). A
  single JSONL file without a manifest only gets an `off_schedule_seed` warning for a train seed that is not among
  the entry's first 10,000 train seeds;
* **manifest**: schema, the three fingerprints and `options` present; listed files exist; record counts, sizes and
  sha256 match; `options.formats` equals the listed formats; `entries` matches the records (every record's entry and
  seed tag listed, per-format counts equal, no listed entry without records) and every entry is in
  `verification.verified`; every seed the options give a verified entry is either exported (in `entries`) or listed
  in `skipped` (so deleting an entry's records together with its `entries` row is caught; not checkable when
  `--max-pairs` capping or dedup removed records); every record carries the manifest's fingerprints and its
  `split` / `obs` options;
* **leaks** in everything except `meta`: underscore or `secret_fields` keys anywhere; non-handle keys in
  `visible_entities`; true entity ids in any string (observations, commands, messages, reasons, instructions). With
  deep checks (default) the validator rebuilds each episode's initial environment from (catalog_id, seed) to know
  the exact entity ids and to resolve handles, then flags fields in an entity's `secret_fields` and never-tier fields
  (the per-entity checks of `tools/perception_audit.py`). In every mode ids are also recognised by shape: a token
  that starts with `<registered type>_<n>` (`fridge_2`, `refrigerator_1_gasket`, `range_radiant_1_lf`) or that has the
  shape of an id the house generator emits (the *static id vocabulary*: the ids of a few generated houses with digit
  runs generalised, e.g. `main_water_valve`, `water_heater_inlet_valve`, `house_key_<n>`, `floor_<room id>`), unless
  it is a visible room / person / pet / doorway id. Building the vocabulary takes about two seconds per process; if no
  house can be generated a `vocabulary_unavailable` warning says the check fell back to type shapes only.

**Deep checks that could not run fail validation.** When the environment cannot be rebuilt for a record (spec
removed, retired or unreadable, build error) that record is a `deep_unavailable` **error**: the exact id and
per-entity field checks did not run. `--allow-static` (`allow_static=True`) accepts such records with the static
checks and a `deep_unavailable` warning; `--no-deep` (`deep=False`) runs the static checks for every record by choice.
`report["deep_checked_records"]` and the CLI say how many records the deep checks covered (among authored
duplicates, the spec whose hash matches the record's `spec_hash` is used).

**Stale datasets.** Records whose fingerprints differ from the current ones get `stale` / `stale_harness` /
`stale_perception` warnings and are otherwise checked as strictly as fresh ones: a simulator edit (which moves
`code_fingerprint`) never weakens a check. Secret fields (underscore or `secret_fields`) are always errors. A
never-tier field is downgraded to a `hidden` warning only when the record's `perception_fingerprint` differs from the
current one (the type tiers really changed since export) **and** the field is not a core privacy / ground-truth field
(`owner, home, value, sentimental, important, intent, decoy, secret_fields, private_contents, belongs_to, assigned_to,
gift_for, truth, answer`), which stay errors in every case.

## Sample

`datasets/sample/` is a small committed export: four entries from different kinds and domains (electrical task,
navigation task, safety appendix entry, mechanisms adaptability entry), one train seed each, all four formats,
verified with `--verify-now`. Its `manifest.json` records the schema and the three fingerprints of the code that made
it; `--validate-dataset` reports `stale` / `stale_harness` warnings, not errors, once the simulator or the evaluation
tooling changes, and a change of the type perception tiers adds `stale_perception`. A new format version (above)
makes the old sample fail validation, so it is regenerated whenever `SCHEMA` changes. Regenerate with:

```
python tools/export_dataset.py datasets/sample --catalog-ids T-5ad61b6881821b-01,T-e780c9db18b3bf-01,X-d734ea3e299b16-01,A-8910a09f802fbf-01 --seeds-per-entry 1 --verify-now --overwrite
python tools/validate_dataset.py datasets/sample
```

## Limitations

* Demonstrations come from privileged reference plans (routing and `avoid` lists computed from true state); they are
  successful and perceivability-checked, not necessarily what an observation-only agent could plan.
* Wrong plans are the spec authors' plausible mistakes, not a sample of agent failures.
* Observations are large (whole-room perception every turn); use `--obs compact`, `--formats` and `--max-pairs` to
  bound size, and the `size` block of the manifest to budget. For scale: one train seed for every candidate spec
  (212 selected, 191 exported) gave 1,643 records / 114 MB in compact mode (sft about 400 KB per record, pairs about
  20 KB, critiques about 40 KB) and took about 15 minutes with `--verify-now --workers 7`.
* Seeds whose reference fails in realistic mode are skipped and listed in the manifest; known causes at the time of
  writing are kernel-side (ask topics with embedded ids, ids without underscores or inside perceived text fields;
  see the dataset component's kernel requests), not dataset filtering.
* The dataset reflects the simulator's symbolic model (docs/PERCEPTION.md "Not modeled", docs/KNOWN_LIMITS.md); it is
  not evidence of real-robot competence.
